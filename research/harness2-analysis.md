# Harness² 원문 분석과 Dupy GTM 적용안

작성·확인: 2026-10-24 KST. 범위: 연구 원문 확인과 설계 제안. Harness² 설치·실험 재현, 데이터 재수집, 유료 미디어 생성, 게시 실행은 하지 않았다. 아래 적용안은 실행된 기능이나 검증된 성과가 아니다.

## 1. 정확히 어떤 연구인가

정식 명칭은 **Harness²: Recursive Agent Harnessing for an Open World**다. 논문은 arXiv **2610.14224v1**, 제출일은 **2026-10-09**다. 저자는 Ruiyao Xu 외 8명이며, 프로젝트는 Northwestern University와 Google Cloud AI Research 소속을 명시한다. [논문 표지·초록](https://arxiv.org/html/2610.14224v1), [저자 프로젝트 페이지](https://harness2.github.io/).

공식 코드 원출처는 [google-research/harness2](https://github.com/google-research/harness2)다. Apache 2.0 연구 코드이며 README는 **공식 지원되는 Google 제품이 아니라고 명시**한다. 오디오 분석 모델의 내장 기능이나 Google Cloud의 운영 서비스로 소개하면 안 된다. 코드 문서는 변경될 수 있으므로 이 보고서는 위 날짜에 읽은 공개 문서 기준이다. 별도의 Google 공식 블로그 글을 출처로 확보한 것은 아니다.

## 2. 원문에서 확인한 구조·근거·한계

다음은 논문 자체의 설명이다. 적용 해석은 다음 절부터 구분한다.

- **변경 대상:** 모델 가중치는 고정하고 실행을 둘러싼 harness를 수정한다.
- **작업 내부:** 기준 실행 후 일반 절차 후보와 도메인 후보를 제안한다. 같은 작업·모델·환경에서 실행한 행동 차이를 보고 변경을 선택·조합하며, 조합한 harness도 다시 실행한다. 기존 버전 유지도 가능하다.
- **작업 사이:** 채택한 harness와 증거가 있는 경험을 라이브러리에 보관한다. 다음 작업은 공통 기본 harness에서 시작해 필요한 요소만 재사용한다. 작업 내부에서는 개선 라이브러리를 고정한다.
- **재귀 예산:** parallel은 후보 탐색 폭, sequential은 연속 개선 깊이를 늘린다. 복수 최종 산출물은 익명화해 고르며 채택이 최적성 증명은 아니다.
- **실험:** WorkBuddy-Bench·JobBench·LAB, GLM-5/오디오 분석 모델 3.5 Flash × OpenCode/Codex, 3회 평균·표준편차를 보고한다. 기본 편집자는 Claude Opus 4.8이다.
- **검증 경계:** 행동 대조는 정답 검증이 아니다. 선택 오류·공유된 잘못된 전제·실행 변동으로 회귀가 발생한다. 추가 실행·편집 비용이 들고 전이를 보장하지 않는다.

출처: [논문 §2–3, Appendix E.6/F](https://arxiv.org/html/2610.14224v1). 저자 실험을 읽었으며 독립 재현은 하지 않았다.

대표 수치는 다음과 같다. 서로 다른 평가 단위를 합쳐 하나의 향상률로 표현하지 않는다.

| 같은 구성, Harness² k=1 | 77.5 | +5.1점 |

README의 수정 표면은 system prompt, guardrails, memory, tool guidance, subagents, skills, scripts, plugins의 8종이다. 실행기는 OpenCode와 Codex를 지원한다. 작은 데모는 모델 인증 없이 실행할 수 있지만 모델 기반 benchmark는 비용이 발생한다. README는 실행기의 제한 없는 네트워크와 Codex sandbox 비활성화를 밝히며, 평가 정답 접근을 막는 네트워크 제한을 요구한다. [공식 README](https://github.com/google-research/harness2#readme).

## 3. Dupy에 적용할 핵심 판단 — 아래는 설계 해석

**7단계 콘텐츠 루프 위에, 그 루프의 지시·도구 사용·평가 방식을 고치는 별도 개선 루프를 둔다.** 매번 모든 단계를 다시 만들거나, 직전 게시물에서 반응이 좋았던 표현을 영구 지침으로 덧붙이는 방식은 피한다.

두 종류의 개선은 구분해야 한다.

1. **콘텐츠 수정:** 훅, 사용 장면, CTA, 장면 길이, 발음 등을 고쳐 현재 결과물의 품질을 높인다.
2. **harness 수정:** 왜 같은 오류가 반복되는지 찾아 기획 스킬, 입력 계약, 참조 선택 규칙, 검수 절차나 재시도 조건을 고친다.

‘후보 세 개 중 best 1 선택’은 현재 콘텐츠 선택이다. Harness²처럼 만들려면 **어떤 스킬·절차 변경이 어떤 행동 차이를 만들었는지** 비교 기록도 있어야 한다. 좋은 결과물 하나를 골랐다는 사실만으로 스킬이 좋아졌다고 결론내리지 않는다.

운영은 안정된 기본 스킬 버전에서 시작하고, 개선기는 별도 버전의 변경안을 만든다. 기존 기획 자료를 고쳐 쓰는 동안 기본 스킬을 덮어쓰지 않는다. 새 변경은 오프라인 비교에서 근거가 생긴 뒤 채택하고, 다음 작업부터 사용한다.

## 4. 사용자가 정한 7단계에 붙일 입출력·평가 계약

이 표는 Dupy GTM 운영 설계다. Dupy 제품 내부 생성 엔진을 교체한다는 뜻이 아니다. 영상 생성 모델와 음성 생성 모델 사용자가 지정한 향후 제작 경로이며, 이번 조사에서 실제 제공 여부·API·가격·입력 지원을 확인하지 않았다.

| 단계 | 입력과 할 일 | 반드시 남길 결과 | 통과 조건·다음 행동 |
|---|---|---|---|
| 1. 자기 Instagram/Threads 성과 분석 | 연결된 인앱브라우저 계정 지표와 게시물 스냅샷 | 계정·기간·수집시각·지표 정의, 잘된/안된 패턴과 근거 게시물 ID | 관측 불가를 0으로 채우지 않음. 조회수·도달·좋아요·전환을 구분하고 부족한 근거를 표시 |
| 2. 시장·레퍼런스 | TikHub 자료와 사용자가 지정한 추적 채널, 기존 저장 자료 | 원본 URL·채널·게시일·수집일·반응 근거·영상 전개 요약 | 반복 수집 전 저장 자료·48시간 CLI cache 재사용. 채널 크기와 게시 후 경과시간을 고려하고 비교 불가 지표 표시 |
| 3. 주제 기획 | 1·2의 증거, Dupy 제품 사실, 사용자·상품 시나리오 | 후보별 hook/use scene/CTA, 참조한 구조와 Dupy에서 바꾼 내용 | 새 창작을 기본으로 삼지 않고 레퍼런스의 설득 구조를 Dupy에 변주. 실제 기능과 메시지 가설을 구분 |
| 4. 기획 리뷰·best 1 | 후보를 같은 형식으로 익명화해 검토 | 선택한 후보 ID, 선택 근거, 탈락 사유, 고쳐야 할 부분 | Dupy 타깃의 구체적 문제·시연 가능성·첫 3초 이해·CTA 연속성. 모두 기준 미달이면 무리하게 하나 고르지 않고 3으로 반환 |
| 5. 콘텐츠 생성 | 선택 기획, 원본 video reference, 전용 인플루언서 사진, 배경사진, 음성 입력 | 제공자·모델/설정·입력 파일 식별값·job ID·원가·완성 파일 | 준비물과 사용 권한·예산·작업 모드 확인 후 실행. 현재는 설계만 하므로 생성 호출 없음 |
| 6. 실제 시청 평가 | 완성된 영상과 오디오, 기획 계약 | 타임코드별 관측·실패 원인·수정 요청·최종판 파일 ID | 전 구간 영상·음성 확인. 얼굴/배경 연속성, 화면·자막·음성 정합, 기능 주장, CTA 검수. 파일이 없으면 평가 완료 불가 |
| 7. 포스팅 agent | 검수를 통과한 정확한 파일, 문구·계정·시간·게시 권한 범위 | 요청 ID·플랫폼 post ID·실제 URL·게시 확인 상태 | 파일/문구 변경 시 검수 무효화. 게시 성공은 실제 게시물 조회로 확인하고, 다음 성과 관측을 1로 연결 |

제품 사실의 출발 문서는 [Dupy 제품 SoT](<project-root>/research/dupy-product-sot.md)다. 이 조사에서는 해당 문서를 읽었으며, 그 안의 제품 UI·코드를 독립적으로 재검증하지 않았다. 실제 제품 동작·수익 증거와 광고 제작 연출을 혼동하지 않는다.

## 5. Dupy용 Propose–Probe–Compose

초기 적용 단위는 **같은 레퍼런스·같은 제품 사실 묶음에서 기획과 리뷰까지**로 작게 잡는 것이 적절하다. 아래는 연구 개념을 비용에 맞게 축소한 제안이며, 원논문 알고리즘의 재현이라고 부르지 않는다.

1. **기준 실행:** 고정된 자료 묶음으로 기존 기획·리뷰 스킬의 결과와 판단 경로를 저장한다.
2. **Propose A — 절차:** 예를 들어 “상품 기능 나열 때문에 훅이 늦음”이라는 관측이 있으면, 설명 전에 사용 장면을 지정하도록 기획 순서를 바꾼다.
3. **Propose B — 도메인:** 예를 들어 “제휴 수익 자동화를 현재 기능처럼 말함”이라는 관측이 있으면, Dupy 제품 사실과 목표 메시지를 대조하는 절차를 추가한다.
4. **Probe:** 자료·모델·평가표를 고정해 A와 B를 실행한다. 달라진 기획과 행동을 비교한다. 반복 실행을 했다면 그 변동도 남긴다.
5. **Compose:** 지지된 부분만 채택한다. 충돌하면 수정하거나 하나만 유지한다. 근거가 없으면 기준판을 유지한다. 조합판도 다시 기획·리뷰하여 새 실패가 없는지 확인한다.
6. **업데이트:** 이번 작업의 결과와 증거를 묶고, 다른 레퍼런스에 적용 가능한 교훈만 개선 라이브러리에 적는다.

실제 생성 품질을 고쳤다는 주장을 하려면 이후 승인된 제작에서 바뀐 절차로 만든 영상을 실제 시청해 비교해야 한다. 기획 비교만으로 영상 생성 모델 출력 품질이 좋아졌다고 쓰지 않는다. 게시물 반복 게시는 probe 수단으로 쓰지 않는다.

초기 예산은 **기준 1 + 절차 후보 1 + 도메인 후보 1 + 조합판 1**의 기획 실행을 제안한다. 이는 운영 시작용 예산 가설이다. 효과가 확인되기 전부터 매 게시물마다 큰 병렬 실행이나 전체 영상 재생성을 요구하지 않는다. 변경을 적용해도 행동이 같거나 새로운 증거가 없으면 해당 개선 실험을 종료한다.

## 6. 상태와 근거를 결과물에 묶기

작업별 최소 상태는 다음처럼 둘 수 있다. 이름은 제안이며 구현된 저장 형식이 아니다.

```text
analysis_ready → references_ready → plans_ready → plan_selected
→ production_ready → media_ready → review_passed → publish_ready
→ publishing → published → observed
```

어느 단계든 `needs_input`, `retryable_failure`, `blocked`, `cancelled`을 별도 상태로 기록한다. `media_ready`와 `review_passed`, `publish_ready`와 `published`를 합치지 않는다. Threads 글만 만드는 작업은 영상 생성·시청을 억지로 완료 처리하지 않고 그 포맷에 맞는 본문·링크 검수 경로를 정의한다.

작업 기록의 최소 항목:

- `run_id`, 포맷, 목적, 계정, 현재 단계, 단계별 입력·출력 URI.
- `source_snapshot`: 출처 ID, URL, 수집시각, 지표 원래 명칭, 값/결측 상태.
- `harness_version`, 바뀐 스킬·스크립트, 변경 가설, 기준판과 후보판의 차이.
- `selected_plan_id`, 원본 참조 영상, 인물·배경·음성 asset ID와 식별값.
- `review`: 정확한 파일 ID, 평가표 버전, 실제 관측 타임코드, 실패·해결 여부.
- `budget`: 계획 상한, 실제 호출/비용, 남은 재시도 횟수, 제공자 job ID.
- `publish`: 계정·파일·문구 식별값, 게시 요청키, 플랫폼 ID/URL, 외부 확인 상태.

스킬에 최근 조회수나 특정 게시물의 일시적 패턴을 영구 사실처럼 써넣지 않는다. 일반 절차는 스킬, 이번 작업의 사실은 해당 작업 자료, 재사용 교훈은 라이브러리로 둔다. 생성기와 리뷰어는 같은 원본 자료를 받되, 리뷰어에게 제작자의 자기평가 점수를 먼저 보여주지 않는다.

## 7. 평가: 사전 품질과 사후 성과를 나누기

**게시 전:** 근거 없는 제품 주장, 읽을 수 없는 핵심 화면, 잘못된 링크·계정, 실패한 파일, 불일치한 얼굴·음성, 검수 안 된 최종 수정은 통과시키지 않는다. 나머지는 이해하기 쉬운 훅·사용 장면의 구체성·전개 밀도·CTA 연결을 같은 기준으로 비교한다. 이 평가표는 Dupy가 정의할 계약이며 연구가 정답으로 제공하는 표가 아니다.

**게시 후:** 실제 계정에서 확보 가능한 지표만 사용한다. 인지 목적의 도달/재생, 관심의 프로필 방문/클릭, 제품 사용의 가입/유효 상품 입력/첫 결과 완료를 목적에 맞게 연결한다. 연결 증거가 없으면 재생수를 매출로 읽지 않는다. 측정 창과 표본 수를 사전에 정하고 동일 기간·비슷한 포맷끼리 본다.

성공한 한 편은 다음 실험 후보를 만드는 증거다. 전체 스킬을 바꿀 근거로는 부족할 수 있다. 게시 시각·소재·기존 팔로워·유료 노출 등 혼입 요인을 기록하고, 재현 가능한 절차 개선과 이번 소재만의 효과를 구분한다. 성과가 나쁘면 생성기 설정을 무조건 바꾸기 전에 타깃·참조 선택·기획·노출·전환 연결 중 어디서 문제가 시작됐는지 확인한다.

## 8. 실패 복구와 개선 기록

| 실패 | 복구 규칙 제안 | 재사용할 교훈의 형태 |
|---|---|---|
| 로그인 만료·자기 지표 미노출 | 세션/권한 상태를 확인하고 근거 부족으로 표시. 시장 지표로 자기 성과를 대체하지 않음 | 어떤 화면·권한에서 어떤 지표가 관측되는지 |
| TikHub 오류·Cloudflare 1010 | HTTP만 보지 않고 payload 확인. 기존 cache/저장 JSON 검토. 같은 유료 호출의 무작정 반복 금지 | 검증된 endpoint·필수 인자·중단 조건 |
| 레퍼런스가 Dupy와 안 맞음 | 가장 이른 오류인 2로 돌아가 타깃·사용 장면 기준을 조정 | 어떤 패턴이 어떤 Dupy 시나리오에서 안 맞았는지 |
| 기획 후보 모두 미달 | 미달 근거를 명시하고 3 재기획. 최고점이라고 자동 통과시키지 않음 | 리뷰 항목의 모호함인지 입력 부족인지 |
| 생성 실패·응답 유실 | job 상태 확인 후 기존 결과 회수 우선. 재요청은 남은 예산과 중복 생성 가능성을 확인 | job ID·회수 방법·실패 단계 |
| 시청 중 결함 | 타임코드와 최소 수정 단위 명시. 영향을 받은 장면/오디오와 최종 조립 검수 | 특정 입력·설정이 실제 만든 결함 |
| 게시 응답 유실 | 플랫폼의 게시 존재 여부를 조회하고 대조. 미확인 상태에서 재게시하지 않음 | 중복 방지 식별값과 조회 절차 |
| 게시 후 문제 발견 | 자동 삭제·재게시를 복구 기본값으로 두지 않음. 노출 상태와 수정 범위를 보고 권한 안에서 대응 | 어떤 사전 검수 항목이 놓쳤는지 |

개선 항목 하나에는 **상황 → 관측 실패 → 변경 → 비교 증거 → 채택/기각 → 적용 범위 → 재확인 조건**만 적는다. “좋은 훅을 써라”, “검토를 철저히 해라”처럼 행동이 달라지는지 알 수 없는 지시는 교훈으로 누적하지 않는다. 라이브러리의 오래된 제품 사실·제공자 동작은 재사용 시 다시 확인한다.

## 9. 지금 적용할 범위와 다음 검증

지금은 7단계 스킬 래핑과 단계별 자료·상태·평가 계약을 만드는 것이 우선이다. 이번 설계의 산출물은 해당 계약이며 영상이나 게시물이 아니다.

다음 검증은 저장된 레퍼런스와 제품 사실 묶음 하나로 **기획·리뷰 경로만** 실행해 입력 누락, 후보 추적, best 1 근거, 실패 반환, 변경안 비교 기록이 남는지 확인하는 것이다. 그 뒤 사용자가 제작을 지시하면 제공자 입출력·가격·파일 회수 방법을 그 시점에 확인하고, 단일 영상 생성과 실제 시청 검수로 범위를 넓힌다. 게시 agent는 정확한 계정·최종본·문구와 사용자에게 승인된 게시 범위를 만족하는 실행만 맡는다.

**판단:** Harness²에서 가져올 가장 중요한 구조는 “좋아 보이는 결과물 선택”보다 **실행 증거를 바탕으로 작업 방식을 고치고, 그 개선 경험을 다음 작업에 제한적으로 재사용하는 방식**이다. Dupy의 실제 성장 효과는 별도 운영 데이터로 확인해야 한다.
