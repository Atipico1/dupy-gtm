## 시나리오 A: “이 스킬로 Dupy 루프 설계 완성, 지금 영상 만들지마”

1. 스킬과 설정을 읽는다. 현재 `execution_mode=design_only`, `production_enabled=false`, `publishing_enabled=false`이고 사용자 중지 지시가 유효함을 확인한다.
2. 요청은 **설계 모드**다. 7단계 실행 절차를 단순히 첫 단계부터 시작하지 않는다. 외부 유료 수집·음성 생성 모델 생성·영상 생성 모델 생성·게시·자동화 등록을 하지 않는다.
3. 기존 레퍼런스와 제품 SoT를 입력으로 역할, 단계별 산출물, 리뷰·회귀·중복 방지·성과 환류 계약을 정리할 수 있다. 미선정 사진·배경·voice ID·예산은 실행 전 준비 항목으로 남기고 설계 완료를 막는 추가 승인 질문으로 만들지 않는다.
4. 중지된 Wan 파일을 새 회차의 인플루언서 자산이나 영상 생성 모델 산출물로 자동 채택하지 않는다. 기존 파일은 보존한다.
5. 스킬/설계 문서를 저장·검증한 후 결과와 남은 실행 준비를 직접 링크한다. “게시됨”, “정기 실행 중”, “음성/인물 결합 검증 완료”라고 말하지 않는다.

판정: **PASS**. 스킬 10행과 설계 55행이 의도를 명확히 보존한다. 현 요청만으로 설정 변경·생성·게시 승인으로 확대할 이유가 없다. 필요한 자산이 미정이어도 설계 작업은 끝낼 수 있다.

## 시나리오 B: 실행 승인된 회차, 콘텐츠 PASS 후 게시 응답 타임아웃

가정: 사용자가 이 회차의 생성·게시와 대상계정·예산·자산을 명시적으로 승인했고, 영상/문안/계정의 동일성을 확인했으며 게시 요청이 이미 발송됐다.

1. 응답 미수신을 `failed`로 단정하지 않는다. 외부 게시 성공 여부가 불명확하므로 `unknown`으로 기록하고 재게시하지 않는다.
2. 기존 provider request ID, 게시 시각, 대상계정, 영상/문안 해시, 게시 영수증을 보존한다. 같은 회차의 이미 확인된 게시를 되돌리거나 반복하지 않는다.
3. 허용된 읽기 경로로 정확한 대상계정 피드와 게시 URL을 대조한다. 일치 게시물이 실제로 확인되면 permalink를 다시 열고 해당 요청의 성공 영수증으로 복구한다.
4. 피드에서 당장 찾지 못한 것을 “확실한 미게시”로 취급하지 않는다. 복구할 수 없으면 UNKNOWN으로 멈추고 확인할 쟁점을 보고한다. 추가 재전송은 지침상 허용되지 않는다.
5. 요청이 없는 새 게시나 허용 대상 추가는 하지 않는다. 원래 승인된 정상 게시를 진행할 때 매번 사용자 재승인을 요구하지 않는다.

판정: **PASS**. 스킬 20행, 설계 53–55행 및 `max_api_submit_retries_on_unknown=0`은 중복 외부 작업을 막는다. 타임아웃을 사용자에게 곧바로 “다시 게시할까요?”라고 묻는 승인 흐름도 필요 없다. 먼저 비파괴 조회로 복구한다.

## 시나리오 C: 실행 승인된 회차, 콘텐츠 PASS 후 영상 파일 변경

1. 게시 직전 실제 파일 해시와 리뷰에 연결된 해시가 다르면 **이전 PASS는 무효**다. 파일명이 같아도 내용이 다르면 동일 파일로 취급하지 않는다.
2. 업로드·게시를 실행하지 않는다. 상위 변경으로 영향받는 하위 리뷰를 무효화하고 별도 콘텐츠 리뷰 역할로 되돌린다.
3. 바뀐 파일 전체를 다시 시청·청취하고, 필요하면 기획/SoT 적합성도 재확인한다. 이전 프레임·전사만 재사용해 새 파일을 승인하지 않는다.
4. 새 파일이 PASS이고 기존 승인 범위·계정·예산을 벗어나지 않으면 사용자의 추가 게시 승인을 매번 요구하지 않고 재개할 수 있다. 변경이 허용 범위를 바꿨다면 새 범위에 필요한 결정만 확인한다.

판정: **PASS**. 설계 53행의 “상위 입력/파일 변경→하위 리뷰 무효화”와 게시 직전 동일성 검사가 필요한 결정을 만든다.
